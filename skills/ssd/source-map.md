# SSD source-to-operation map

This map distinguishes source-backed SSD operationalization from an agent's architectural preferences. Paths are relative to the repository root. The source corpus is draft material; [source-gaps.md](source-gaps.md) records places where it does not support a required decision.

## Standing of concepts in the current source

| Standing | Concepts | Source basis | Operational treatment |
|---|---|---|---|
| Foundational minimum | entities, relationships, capabilities, constraints | `book/foundations/foundations-01.md`, `foundations-02.md`, `foundations-04.md`, `foundations-07.md` | Reconstruct these before designing a surface. The four primitives are the readiness floor, not necessarily the complete model for every risk level. |
| Semantic backbone | identity, state, transitions, events/history, provenance, boundaries, authority, responsibility, consequences | `book/semantics/semantics-01.md`, `semantics-03.md` through `semantics-10.md` | Make applicable semantics explicit because they determine behavior, power, trust, and auditability. |
| Projection invariants | projection primacy, operator context, intent, human/machine parity | `book/foundations/foundations-05.md`, `foundations-06.md`; `book/dual/dual-01.md` through `dual-03.md`; `book/dso/dso-07.md` through `dso-09.md` | Derive contextual human and agent surfaces from one semantic core; never infer authority or capability from an affordance. |
| Safety consequences | side effects, irreversibility, confirmation gates, uncertainty, escalation, safe stops | `book/semantics/semantics-06.md`, `semantics-08.md`; `book/dual/dual-04.md`, `dual-07.md`, `dual-08.md`; `book/ops/ops-03.md` | Apply when risk or uncertainty warrants them. These are consequences of explicit meaning and responsibility, not additional minimum primitives. |
| Operational concerns | governance, policies, guardrails, observability, incidents, learning, access control, change | `book/ops/ops-01.md` through `ops-08.md` | Use to keep meaning governable, inspectable, adaptable, and safe after design and during operation. |

## Traceability matrix

Each row follows: **source principle → architectural implication → required agent behavior → observable evaluation criterion**.

| SSD source principle | Architectural implication | Required agent behavior | Observable evaluation criterion |
|---|---|---|---|
| The product is a semantic system; screens and flows are derived (`foundations-01.md`, `foundations-05.md`). | A requested UI is evidence about a projection, not the definition of the product. | Reframe a screen-first prompt and model meaning before controls or layout. | Fails if tables, pages, buttons, wizard steps, endpoints, or tools are the primary architecture. |
| Meaning consists operationally of constraints and guarantees about representation, relationships, possible actions, conditions, and effects (`foundations-02.md`). | The model must be explicit enough to make behavior reviewable. | State the relevant guarantees and unknowns, not just nouns and labels. | Passes only if conditions and effects materially shape the design. |
| Entities, relationships, capabilities, and constraints are the minimum viable semantic model (`foundations-07.md`). | Omitting any of the four creates an under-designed feature. | Name all four for the relevant scope before projection work. | Fails if a proposed feature cannot answer the four source litmus-test questions. |
| Entities have identity, state, relationships, and actions independent of representation (`semantics-01.md`). | UI components, rows, and payloads cannot substitute for conceptual anchors. | Identify persistent entities and stable identity; map actions to them. | Fails when “table row,” “card,” “form,” or a JSON shape is treated as the entity without semantic identity. |
| Distinct types require a difference in required relations, lifecycle, validation, or authority (`dso-02.md`). | Presentation, disclosure, transport, or storage variation alone should not proliferate types. | Justify each specialization with a declared semantic delta or keep one type with orthogonal variation. | Fails if types differ only by display, channel, or metadata label. |
| Relationships and typed edges carry meaning; menus flatten it (`foundations-01.md`, `graphnav-01.md`, `graphnav-02.md`). | Navigation and capability context depend on explicit relations. | Name relationships assumed or changed by the design and derive traversal from them. | Fails if relationships are replaced by page hierarchy or menu placement. |
| States are meaningful conditions; transitions encode rules, irreversibility, responsibility, and audit trails (`semantics-03.md`). | Behavior must exist independently of button states or workflow steps. | Name states, legal and forbidden transitions, preconditions, and responsibility. | Fails if disabled controls or step order are the only enforcement. |
| State and presentation variant are different (`dso-03.md`). | Appearance cannot carry product truth. | Classify behavior-changing conditions as state and appearance-only choices as variants. | Fails when styling changes permissions, lifecycle, or allowed actions. |
| Events preserve what happened while states preserve what is (`semantics-04.md`). | Current state alone is insufficient for trust and accountability. | Preserve named transition, timestamp, actor, and reason for material changes. | Fails if the design cannot explain how the current state was reached. |
| Provenance answers who, when, how, and under which authority or rule (`semantics-05.md`). | Trust and safe automation need attributed evidence. | State provenance requirements for information and consequential actions. | Fails when reliability is asserted without inspectable origin or authority. |
| Boundaries must mark scope, authority, time, and confidence; uncertainty must be represented (`semantics-06.md`, `dso-10.md`). | The system must not imply knowledge or certainty it lacks. | Mark uncertainty and boundaries; allow revision; block irreversibility under uncertainty. | Fails when the response fabricates semantics, hides confidence, or lets a projection overstate certainty. |
| Capabilities are first-class declared possibilities to cause change, not affordances (`semantics-07.md`, `foundations-04.md`). | Controls and tools must project capability contracts. | Identify target, inputs, preconditions, effects, postconditions, and responsibility independently of the invoking surface. | Fails if “Delete button” or “delete tool” is the capability definition. Because `semantics-07.md` is truncated, the complete list is also supported by `foundations-04.md`; see the source gap. |
| Side effects affect more than primary intent and can alter entities, permissions, automations, or assumptions (`semantics-08.md`). | Consequence analysis must extend beyond the target state change. | Perform an affected-entity and downstream-consequence sweep. | Fails if the primary result is modeled but collateral changes are ignored. |
| Irreversibility is first-class and cannot be solved by a cosmetic dialog (`semantics-08.md`). | The irreversible boundary, recovery limits, gate, and permanent audit must be semantic. | Name the boundary; prevent accidental execution; block on uncertainty; define escalation. | Fails if “add confirmation modal” is the complete safety response. |
| Ability and authority differ; authority declares who, what action, which entities, conditions, and scope (`semantics-09.md`). | Surface visibility or access to an endpoint does not confer permission. | Define and enforce scoped authority independently from all projections. | Fails if hiding/disabling a control or withholding a tool is the access-control model. |
| Responsibility follows capability and accountability exposes who did what, when, why allowed, and response paths (`semantics-10.md`). | Every consequential capability needs an accountable owner and inspectable reason. | Assign responsibility and make privilege and override use traceable. | Fails when responsibility dissolves into “the system” or action ownership is absent. |
| Operators may be human, automated, or hybrid (`foundations-06.md`, `dual-02.md`). | Operator intent, authority, risk, and feedback requirements cannot be collapsed into a generic “user.” | Identify distinct operators and their intent, authority, constraints, and responsibility. | Fails if administrators, end users, services, and agents are treated as interchangeable. |
| Intent must declare desired outcome, reason, constraints, and acceptable risk (`dual-03.md`). | A click or call is insufficient context for accountable action. | Capture intent for consequential capabilities and preserve it as evidence. | Fails if the agent infers purpose solely from an affordance or call. |
| Confirmation gates validate intent, authority, consequence awareness, and absence of blocking uncertainty (`dual-04.md`). | A gate is a semantic checkpoint, not generic friction. | Require gates for irreversibility, privilege escalation, effects on others, and action under uncertainty. | Fails if the response uses an uninformative “Are you sure?” or lets agent confirmation bypass validation. |
| Human and machine surfaces are equal projections with strict semantic parity (`dual-01.md`, `dso-09.md`). | There is one system meaning, exposed differently for comprehension or determinism. | Derive both projections and compare identity, rules, authority, effects, safety, explanation, and audit. | Fails if tools mirror buttons, rules differ by channel, or agent-only power is not human-understandable. |
| Explanations answer what, why, cause, rules, and confidence (`dual-05.md`). | Explainability is an operator surface rather than debug output. | Provide contextual, risk-proportional explanations traceable to rules and provenance. | Fails if the design provides logs or rationale prose without rules, causes, or confidence. |
| Audit surfaces are navigable, temporal, actor/rule-linked, and retroactively immutable (`dual-06.md`). | Raw logs are insufficient for accountability. | Define human and agent audit access by entity, actor, transition, and rule. | Fails if evidence exists but cannot support investigation or has mutable history. |
| Escalation is a transition of authority preserving cause, blockage, needed decision, and context (`dual-07.md`). | “Ask a human” is not a sufficient failure path. | Define escalation trigger, recipient/owner, transferred authority, preserved context, and blocked action. | Fails if escalation lacks a decision request or loses execution context. |
| A safe stop preserves context and prevents further irreversible action (`dual-08.md`). | Halting is a protective state with recovery, not a crash or blind retry. | Stop on low confidence, conflicting constraints, ambiguous authority, dependency failure, or unexpected side effects. | Fails if the agent guesses, repeatedly retries past a guardrail, or halts without preserving recovery context. |
| Policies state what should happen; guardrails state what must not happen (`ops-02.md`, `ops-03.md`). | Adaptive rules and non-negotiable safety boundaries need distinct treatment. | Name contextual inputs to policy and deterministic guardrail responses. | Fails if advice, policy, validation, and hard safety boundaries are conflated. |
| Observability is semantic visibility of actions, state changes, constraints, policies, guardrails, and actors (`ops-04.md`). | Dashboards and raw logs do not establish governability. | Link causes to rules and effects to entities in real time and history. | Fails if the proposed telemetry cannot answer what the system is doing and why. |
| Access control distributes power and agent authority must be scoped, expiring, escalation-only where appropriate, and auditable (`ops-07.md`). | Long-lived unbounded agent authority is a critical risk. | Apply least privilege, expiration, explicit escalation, and privilege-use logging. | Fails if an agent receives broad persistent authority merely because its tool supports it. |
| Semantic change affects definitions, relations, constraints, policies, capabilities, and authority (`ops-08.md`, `dso-11.md`, `dso-12.md`). | Meaning must evolve through impact analysis, versioning, coexistence, migration, and deprecation. | Identify ripple effects and compatibility when the requested design changes existing meaning. | Fails if the proposal silently changes semantics or treats schema versioning alone as sufficient. |
| Closure requires explicit completion, partial success, unresolved issues, and escalation signals (`graphnav-06.md`). | Operators need to know when intent is satisfied and context is stable. | Define outcome states and return/recovery paths for humans and agents. | Fails when a workflow ends at a screen or response without semantic completion. |
| The agent reading path says not to act if ontology, safety, accountability, or halting conditions are missing (`reading-paths/path-ai-agent.md`). | Readiness is conditional on meaning, not output fluency. | End as ready, provisional, or safe stop and name missing prerequisites. | Fails when unknowns are guessed to make the answer look complete. |

## How to cite this map in an analysis

Use repository-relative paths in the decision trace. Cite the chapter that actually caused the decision, not this map alone. Classify a decision as:

- **direct principle** when the source states the obligation;
- **operational consequence** when the behavior is the shortest execution step required to satisfy the stated obligation;
- **open source gap** when the source does not select among architectural choices.

If an operational consequence introduces domain policy, a numeric threshold, a default authority scope, or a recovery guarantee not present in the problem or source, it has crossed into invention and must be reclassified as open.
